# SealSkin 0.5.0

The home page is a dashboard now, and an administrator shapes more of what a
user lands in: dashboards of tiles and live widgets laid out per group, a
brand per host name or group, applications baked on top of the ones a store
ships, and browser policies their sessions start under. A link on a dashboard
can open inside a running session, which reaches what only the server's
network does, and a session nobody is connected to can be stopped after a
limit.

## Highlights

* **Dashboards.** The home page is one grid, twelve cells wide, of
  applications, links, link bundles, widgets, and headings. An administrator
  lays dashboards out for groups and users, as tabs in the order they are
  listed, and may lock one or make it a kiosk; a user rearranges the one they
  are given, adds tiles and pages of their own, imports a browser's bookmarks
  file, and exports a page, with those changes kept in their browser.
  **Appearance** sets the background, the look of the tiles, the density, and
  an accent color. Icons come from Font Awesome, from the dashboard-icons,
  selfh.st, Simple Icons, and Material Design packs the server fetches and
  serves itself, from an upload, or from the site's own icon. With no
  dashboard defined, everyone sees the built-in page as before.
* **Widgets.** A widget library an administrator defines once, with the
  groups and users that may see each: clock, stocks, weather, feed (RSS,
  Atom, JSON Feed, with OPML import), calendar (iCalendar), API values in the
  shape of Homepage's `customapi` widget, which is pasted in as YAML, site
  monitor, notice, custom frame, embedded page, and notes. The server reads
  every widget's data, so an address may be one only the server reaches, and
  `{{secret.NAME}}` in an address, header, or body is filled in on the node
  and never sent to a browser. A custom frame runs the administrator's own
  HTML and script in a sandboxed frame with an origin of its own. A user adds
  clocks, notes, weather, stocks, and, where allowed, feeds and calendars by
  address, which the server fetches only on the public internet.
* **Links into sessions.** A link set to open **In a session** opens in a
  browser running inside the server's network, so a dashboard reaches
  internal services from anywhere with nothing but SealSkin exposed. An
  address that looks internal picks this by itself; a running session of the
  application is handed the address and brought forward rather than a new
  one started; a link may leave through a VPN profile; and an administrator's
  link may show whether its address answers. In an administrator's link
  `{username}` becomes the signed-in user's name.
* **The Bakery.** Bake a new application on top of an installed one:
  packages, files, certificates, fonts, anything a Dockerfile can do, under a
  name and an icon of its own. **Guided** mode is a list of steps beside the
  Dockerfile they render to: install packages, with a search of what the
  image can install, add an application (Chromium, Firefox, Google Chrome,
  Brave, Visual Studio Code), Ubuntu PPAs, downloads, development kits
  (Python, Node.js, Rust, Go, Java), Docker, desktop entries, launch
  commands, fonts, copied files, trusted certificates, environment, proxy and
  mirrors, and scripts run at start. **Developer** mode is the Dockerfile
  itself. **Build a trial** builds a draft and opens a session on it without
  changing what users run; a saved recipe is built by every node of a
  cluster and rebuilt whenever its application's image is pulled again. The
  App Laboratory takes a baked application as a base. The Bakery needs the
  Docker provider.
* **Browser policies.** A named set of the policies Chromium and Firefox take
  from an administrator, picked per application in its install dialog and
  mounted read-only into every session of it, where Chromium, Google Chrome,
  Brave, Edge, Opera, Vivaldi, Firefox, LibreWolf, Zen, and Mullvad Browser
  read it. The editor has a tab per engine over every policy the engine
  reads on Linux, from catalogs built out of the engines' own definitions at
  pinned revisions, with the engines' translations, a switch per Chromium
  setting for **Users may change this**, and a JSON view that takes an
  existing policy file whole.
* **A brand per host name or group.** Beside the brand everyone sees, a brand
  of its own for the host names the web app is reached at
  (`portal.example.org`, `*.example.org`), for the members of groups, or
  both: name, logo, accent color, wallpaper, and home page links. The
  sign-in page and the installed web app wear the brand of the host name; a
  group's brand shows after the sign-in.
* **An idle limit.** `session_idle_minutes`, per user or per group, stops a
  session nobody has had open for that many minutes. A session left open in
  a tab counts as open, and so does one whose image does not report its
  connections.

## Server

* Docker session containers are named `sealskin-<first eight characters of
  the session id>-<suffix>`, the prefix a Kubernetes session pod already
  has, in place of Docker's random names.
* A server refuses to start while Docker runs another container under its
  name, since a server's name is its identity in its records and its cluster.
* `POST /api/sessions/<id>/open_url` hands a web address to a running
  session's application, which opens it beside what it has open.
* An address a launch opens is `http`, `https`, `ftp`, or a `magnet` link
  with no spaces, so nothing shaped like an option reaches the application's
  command line.
* An uploaded application icon is read as a PNG, JPEG, WebP, GIF, ICO, or BMP
  picture and kept as a PNG at most 512 pixels wide; anything else is
  refused.
* Every page the server serves runs only its own scripts, under a
  Content-Security-Policy; the room's page adds the workers it builds, and a
  frame widget's page is sandboxed into an origin of its own.
* Dashboard links are `http`, `https`, or a scheme
  `SEALSKIN_DASHBOARD_LINK_SCHEMES` lists (`mailto`, `tel`, `ssh`, `sftp`,
  `rdp`, and `vnc` by default); `javascript`, `data`, `file`, and the other
  schemes a browser runs inside the page are refused whatever is listed.
* A user's own widget and a site icon a user asks for are fetched only when
  every address the name resolves to is public, at every redirect, with no
  credential.
* The user and group settings **Allow Customizing the Home Page**, **Allow
  Own Links**, and **Allow Own Feeds and Calendars**, all on by default.
* New settings: `SEALSKIN_DASHBOARDS_PATH`, `SEALSKIN_WIDGET_SECRETS_PATH`,
  `SEALSKIN_DASHBOARD_LINK_SCHEMES`, `SEALSKIN_WEATHER_URL`,
  `SEALSKIN_STOCKS_URL`, `SEALSKIN_GEOCODING_URL`, `SEALSKIN_BAKERY_PATH`,
  `SEALSKIN_BAKERY_BUILD_IDLE_SECONDS`, `SEALSKIN_BROWSER_POLICIES_PATH`, and
  `SEALSKIN_BROWSER_POLICY_FILES_PATH`.
* The shared store gains `dashboards/`, `bakery/recipes.yml` with the files
  recipes copy under `bakery/files/`, `browser_policies.yml`, and the
  pictures of each brand; widget secrets, baked images, and policy files stay
  with each node.
* **Installed Apps** lists every application under the one it is built on,
  and an application cannot be deleted while a baked application or a
  meta-app is built on it.
* A launch reports a `baking` stage while a recipe builds at an application's
  first launch on a node.
* The VPN image is built without a layer cache, so every build takes
  Alpine's current packages.
* Dependency updates for the server, the documentation site, and the
  workflows.

## Client

* The pencil beside the search box opens edit mode, where tiles are dragged
  and resized, **Add a tile** and **New page** add to the page, and
  **Appearance** takes the place of the brush.
* Starring an application puts a tile of it on the page; a tile carries a
  mark while a session of it runs, and one two rows high or more shows that
  session's desktop.
* The admin dashboard gains the **Bakery** and **Browser Policies** tabs, the
  brand picker in **Branding**, and the browser policy of an application in
  its install dialog.
* The mobile app's Capacitor packages and build dependencies are updated to
  their patched releases.
* Translations for the dashboards, brands, the Bakery and its guided steps,
  the browser policy editor, and the idle limit in all seventeen other
  languages.

## Upgrading from 0.4

Nothing on disk needs changing, and nothing new is on until an administrator
sets it up: with no dashboard defined the home page is the built-in one, and
`session_idle_minutes` is `-1`, no limit. What is new:

* A user's favorites become tiles of their page, and the background they set
  with the brush is under **Appearance** in edit mode.
* Docker session containers are named `sealskin-<session>-<suffix>`. Anything
  that picked them out by Docker's random names, or by another pattern, needs
  the new one.
* A server that shares its name with another running container no longer
  starts. Stop that container, or give the server a name of its own through
  its container's name or `SEALSKIN_NODE_NAME`.
* Browser policy files are written under
  `/storage/sealskin_browser_policies` (`SEALSKIN_BROWSER_POLICY_FILES_PATH`),
  beside the home directories, and on Kubernetes on the storage claim. A
  policy holds
  only where sessions run without root: turn on desktop hardening for the
  users it is meant to hold.
* A policy with a Firefox part stands in place of an image's own
  `policies.json`, so LibreWolf's and Mullvad Browser's shipped defaults do
  not apply under it.
* The Bakery builds with the node's Docker daemon, using Docker's classic
  builder, and gives a build no registry credential. On Kubernetes the tab
  says so and recipes cannot be saved.
* The weather and stocks widgets read Open-Meteo and Yahoo Finance once one
  is placed. A deployment without internet access points
  `SEALSKIN_WEATHER_URL`, `SEALSKIN_GEOCODING_URL`, and `SEALSKIN_STOCKS_URL`
  at hosts of its own, or leaves those widgets out.
* In a cluster each node needs the widget secrets its widgets name, as files
  under `SEALSKIN_WIDGET_SECRETS_PATH` or as `SEALSKIN_WIDGET_SECRET_<NAME>`
  variables; the store holds only their names.
* An address handed to a launch that is not `http`, `https`, `ftp`, or
  `magnet` is refused, as is an application icon that is not a picture.
* The idle limit counts on the session's Selkies reporting its connections;
  a session of an image that does not is never stopped by it.

## Documentation

* A Dashboards page, and sections for the
  Bakery, browser policies, and a brand per host name or group under
  Administration; the API, object store, Kubernetes, and settings pages carry
  the new routes, objects, and settings.
* The threat model states the Bakery, browser policies, the dashboards and
  their widgets, the widgets' fetches and secrets, the brand a request wears,
  and the address a user hands a session, with what each may and may not
  reach.
* Pull requests run **Mobile Unsigned Validation**: an Android debug build
  and an iOS simulator build without signing material, and Capacitor's own
  navigation regression tests.
